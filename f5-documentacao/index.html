1. Fundamentos do F5 BIG-IP

Conceitos essenciais que voce precisa dominar antes de automatizar qualquer coisa no F5.

O que e o BIG-IP? IMPORTANTE

O F5 BIG-IP e uma plataforma de Application Delivery Controller (ADC) que fornece load balancing, seguranca (WAF), SSL offloading, gerenciamento de trafego e otimizacao de performance.

Conceitos Fundamentais ENTREVISTA

ConceitoDescricao
Virtual Server (VS)Ponto de entrada do trafego no F5. Recebe requisicoes dos clientes (VIP - Virtual IP + porta)
PoolGrupo de servidores backend que atendem as requisicoes. O F5 distribui trafego entre eles
Pool Member / NodeServidor individual dentro de um pool (IP:porta)
Health MonitorVerificacoes periodicas nos backends (HTTP, TCP, ICMP ou customizado com send/receive)
ProfileConfiguracoes reutilizaveis (HTTP, TCP, SSL, Persistence) aplicadas ao VS
SSL OffloadingF5 termina SSL/TLS do cliente e comunica com backend via HTTP. Centraliza gestao de certificados
SNAT (Source NAT)Traduz IP de origem para que o backend veja o IP do F5. Automap e o mais comum
PersistenceGarante que um cliente sempre va para o mesmo servidor (sticky sessions)
iRuleScript TCL para manipulacao avancada de trafego em tempo real
PartitionSeparacao logica de configuracoes (multi-tenancy)

Arquitetura Full-Proxy IMPORTANTE

Cliente → [BIG-IP (VS/VIP)] → Pool Member (Servidor)
← conexao cliente     conexao servidor →

Por que Full-Proxy e importante?

  • O BIG-IP termina a conexao TCP/SSL do cliente
  • Abre uma nova conexao TCP com o servidor backend
  • Pode inspecionar, modificar e rotear o trafego em qualquer camada (L4-L7)
  • Permite aplicar iRules, WAF, SSL offloading, compression, caching

Arquitetura Tipica Completa

Clientes (Internet) → [Virtual Server (VIP)] → [iRules] → [WAF/ASM] → [Pool]
↓                       ↓                             ↓
[SSL Profile (Offloading)]                      [S1] [S2] [S3]

2. iRules — Programacao no Data Plane

iRules sao scripts em TCL que rodam diretamente no data plane do F5, permitindo manipular trafego em tempo real com performance extrema.

O que sao iRules? Linguagem de scripting nativa do F5 BIG-IP, baseada em TCL (Tool Command Language). Permitem inspecionar, modificar e redirecionar trafego HTTP/HTTPS/TCP em tempo real, com acesso a headers, cookies, payloads e metadados da conexao.

Eventos Principais IMPORTANTE

EventoQuando disparaUso comum
CLIENT_ACCEPTEDConexao TCP do cliente aceitaFiltro por IP, rate limiting
HTTP_REQUESTRequisicao HTTP recebida do clienteRedirect, rewrite de URL, header manipulation
HTTP_RESPONSEResposta HTTP recebida do backendModificar headers de resposta, inserir cookies
LB_SELECTEDApos o F5 selecionar o backendLogging, override de backend
LB_FAILEDFalha ao conectar no backendFallback, sorry page
CLIENTSSL_HANDSHAKEHandshake SSL completadoDecisoes baseadas em certificado do cliente

Exemplo 1: Redirect HTTP para HTTPS ENTREVISTA

TCL / iRule
## iRule: Redirecionar todo trafego HTTP para HTTPS
when HTTP_REQUEST {
    if { [HTTP::header "X-Forwarded-Proto"] eq "http" || [TCP::local_port] == 80 } {
        HTTP::redirect "https://[HTTP::host][HTTP::uri]"
    }
}

Exemplo 2: Roteamento por URI (Content Switching) IMPORTANTE

TCL / iRule
## iRule: Rotear trafego para pools diferentes baseado na URI
when HTTP_REQUEST {
    switch -glob [HTTP::uri] {
        "/api/*" {
            ## Requisicoes de API vao para o pool de microservicos
            pool pool_api_backend
            log local0. "[IP::client_addr] -> API: [HTTP::uri]"
        }
        "/static/*" -
        "/images/*" -
        "/css/*" {
            ## Conteudo estatico vai para CDN/cache
            pool pool_static_content
        }
        "/admin/*" {
            ## Painel admin - restringir por IP
            if { !([IP::client_addr] starts_with "10.10.") } {
                HTTP::respond 403 content "Acesso negado"
                return
            }
            pool pool_admin
        }
        "/health" {
            ## Health check - responder direto sem ir ao backend
            HTTP::respond 200 content "OK" "Content-Type" "text/plain"
        }
        default {
            pool pool_app_principal
        }
    }
}

Exemplo 3: Rate Limiting por IP

TCL / iRule
## iRule: Limitar requisicoes por IP (maximo 100 req/min)
when HTTP_REQUEST {
    set client_ip [IP::client_addr]
    set current_count [table lookup -notouch $client_ip]

    if { $current_count eq "" } {
        ## Primeiro request deste IP - iniciar contador
        table set $client_ip 1 60                 ## TTL de 60 segundos
    } elseif { $current_count > 100 } {
        ## Limite atingido - bloquear
        log local0. "RATE_LIMIT: IP $client_ip bloqueado"
        HTTP::respond 429 content "Rate limit exceeded."
        return
    } else {
        table incr $client_ip                    ## Incrementar contador
    }
}

Exemplo 4: Inserir Headers de Seguranca IMPORTANTE

TCL / iRule
## iRule: Headers uteis para o backend + seguranca na resposta
when HTTP_REQUEST {
    HTTP::header insert "X-Forwarded-For" [IP::client_addr]     ## IP real do cliente
    HTTP::header insert "X-Real-IP" [IP::client_addr]
    HTTP::header insert "X-Forwarded-Proto" "https"
    HTTP::header insert "X-Request-ID" [TMM::cmp_unit][clock clicks]   ## Rastreabilidade
}

when HTTP_RESPONSE {
    ## Remover headers internos que nao devem ser expostos
    HTTP::header remove "Server"
    HTTP::header remove "X-Powered-By"
    HTTP::header remove "X-AspNet-Version"

    ## Adicionar headers de seguranca
    HTTP::header insert "X-Content-Type-Options" "nosniff"
    HTTP::header insert "X-Frame-Options" "SAMEORIGIN"
    HTTP::header insert "Strict-Transport-Security" "max-age=31536000; includeSubDomains"
}

TCL / iRule
## iRule: Persistencia customizada por cookie
when HTTP_REQUEST {

Boas Praticas em iRules:
  • Evite logica complexa — iRules rodam no data plane, logica pesada impacta performance
  • Use return cedo — saia da iRule o mais rapido possivel
  • Prefira Local Traffic Policies para logica simples — sao mais eficientes
  • Evite HTTP::collect a menos que realmente necessario — consome memoria
  • Use log local0. para debug, mas desabilite em producao

3. iControl REST API — Automacao com Python

A API REST iControl permite gerenciar 100% do F5 BIG-IP programaticamente. Tudo que voce faz na GUI ou tmsh pode ser feito via API.

Autenticacao IMPORTANTE

Dois metodos de autenticacao:

  • Basic Auth: Simples, mas menos seguro. Envia credenciais em cada request
  • Token (Recomendado): Obtem token via /mgmt/shared/authn/login, validade extensivel ate 36000s (10h)
Python
## Autenticacao por token - RECOMENDADO
import requests, urllib3
urllib3.disable_warnings()

def obter_token(host, usuario, senha):
    url = f"https://{host}/mgmt/shared/authn/login"     ## << Endpoint de autenticacao
    payload = {
        "username": usuario,
        "password": senha,
        "loginProviderName": "tmos"
    }
    resp = requests.post(url, json=payload, verify=False)
    resp.raise_for_status()
    token = resp.json()['token']['token']

    ## Estender validade do token para 10 horas
    url_token = f"https://{host}/mgmt/shared/authz/tokens/{token}"
    requests.patch(url_token, json={"timeout": 36000},
                   headers={"X-F5-Auth-Token": token}, verify=False)
    return token

Classe Python Completa para F5 ENTREVISTA

Python
## Script reutilizavel para gerenciar F5 BIG-IP via iControl REST

class F5Client:
    ## Encapsula autenticacao e operacoes comuns

    def __init__(self, host, username, password):
        self.host = host
        self.base_url = f"https://{host}/mgmt/tm"    ## << BASE URL da API
        self.session = requests.Session()
        self.session.verify = False
        self._authenticate(username, password)         ## Autentica no construtor

    def _authenticate(self, username, password):
        auth_data = {
            "username": username,
            "password": password,
            "loginProviderName": "tmos"
        }
        resp = self.session.post(
            f"https://{self.host}/mgmt/shared/authn/login",
            json=auth_data
        )
        resp.raise_for_status()                        ## Lanca excecao se falhar
        token = resp.json()["token"]["token"]
        self.session.headers.update({"X-F5-Auth-Token": token})

    ## ===== POOLS =====
    def list_pools(self):                              ## GET = listar
        resp = self.session.get(f"{self.base_url}/ltm/pool")
        return resp.json().get("items", [])

    def create_pool(self, name, lb_method="round-robin", monitor="/Common/http"):
        payload = {"name": name, "loadBalancingMode": lb_method, "monitor": monitor}
        return self.session.post(f"{self.base_url}/ltm/pool", json=payload).json()

    ## ===== POOL MEMBERS =====
    def add_member(self, pool, ip, port):               ## POST = criar
        url = f"{self.base_url}/ltm/pool/~Common~{pool}/members"
        payload = {"name": f"{ip}:{port}", "address": ip}
        return self.session.post(url, json=payload).json()

    def disable_member(self, pool, member, partition="Common"):
        data = {"session": "user-disabled"}             ## << Desabilita membro
        return self.session.patch(                     ## PATCH = update parcial
            f"{self.base_url}/ltm/pool/~{partition}~{pool}/members/~{partition}~{member}",
            json=data
        )

    def enable_member(self, pool, member, partition="Common"):
        data = {"session": "user-enabled"}              ## << Habilita membro
        return self.session.patch(
            f"{self.base_url}/ltm/pool/~{partition}~{pool}/members/~{partition}~{member}",
            json=data
        )

    ## ===== VIRTUAL SERVERS =====
    def create_virtual_server(self, name, vip, port, pool):
        payload = {
            "name": name,
            "destination": f"/Common/{vip}:{port}",
            "pool": f"/Common/{pool}",
            "sourceAddressTranslation": {"type": "automap"},   ## << SNAT Automap!
            "profiles": [{"name": "http"}]
        }
        return self.session.post(f"{self.base_url}/ltm/virtual", json=payload).json()

    ## ===== iRULES via API =====
    def create_irule(self, name, tcl_code):
        payload = {"name": name, "apiAnonymous": tcl_code}    ## << apiAnonymous = codigo TCL
        return self.session.post(f"{self.base_url}/ltm/rule", json=payload).json()

    def associate_irule(self, vs_name, irule_name):
        url = f"{self.base_url}/ltm/virtual/~Common~{vs_name}"
        current = self.session.get(url).json()
        rules = current.get("rules", [])
        rules.append(f"/Common/{irule_name}")
        return self.session.patch(url, json={"rules": rules})

    ## ===== SALVAR CONFIG =====
    def save_config(self):                             ## << SEMPRE chamar apos alteracoes!
        return self.session.post(
            f"{self.base_url}/sys/config",
            json={"command": "save"}                  ## Equivale a "tmsh save sys config"
        )

## ===== USO =====

Os problemas mais frequentes que voce vai encontrar em producao, com diagnostico e solucao.

Sintoma: Membro do pool aparece com status vermelho (offline) na GUI ou via tmsh.
CausaSolucao
Servico parado no backendsystemctl restart app
Firewall bloqueando health checkVerificar regras de FW entre F5 e backend
Monitor com send/receive incorretoAjustar string esperada no monitor
Timeout do monitor muito curtoAumentar intervalo/timeout
Problema de rede (VLAN/rota)Verificar self IPs, VLANs e rotas

Problema 2: Virtual Server Nao Responde ENTREVISTA

Sintoma: Usuarios nao conseguem acessar a aplicacao via VIP. Timeout ou conexao recusada.

Checklist de investigacao:

  1. VS esta enabled e available?
  2. Pool tem membros available?
  3. Perfil SSL correto e certificado valido?
  4. SNAT configurado (automap ou snatpool)?
  5. Regras de firewall permitem trafego ao VIP?
  6. DNS resolve para o IP correto do VIP?
  7. Self IP e VLAN configurados corretamente?
  8. Persistence profile esta correto?
  9. iRules nao estao bloqueando trafego?

Problema 3: Alta Utilizacao de CPU

Sintoma: F5 lento, dashboard mostrando CPU acima de 80%.
CausaSolucao
iRules ineficientesOtimizar logica, evitar regex complexo
Excesso de conexoesVerificar connection limits e timeouts
SSL handshakes excessivosImplementar SSL session reuse/caching
Ataque DDoSAtivar DoS protection profiles
Logging excessivoReduzir verbosidade

Problema 4: Persistencia de Sessao Falha

Sintoma: Usuarios perdem sessao/login durante navegacao. Cada request vai para um backend diferente.
CausaSolucao
Sem persistence profileAdicionar cookie ou source_addr persistence
Cookie com nome/path erradoVerificar configuracao do cookie insert
Timeout muito curtoAumentar persistence timeout
Fallback nao configuradoAdicionar fallback persistence (source_addr)

Problema 5: Certificado SSL Expirado IMPORTANTE

Sintoma: Navegador mostra erro de certificado. Conexoes HTTPS falhando. 
Python
## Verificar certificados proximos da expiracao
def verificar_certificados(client, dias_alerta=30):
    url = f"{client.base_url}/sys/crypto/cert"
    certs = client.session.get(url).json().get("items", [])

    for cert in certs:
        nome = cert.get("name", "unknown")
        expiration = cert.get("apiRawValues", {}).get("expiration", "")
        if expiration:
            from datetime import datetime
            exp_date = datetime.strptime(expiration, "%b %d %H:%M:%S %Y %Z")
            dias = (exp_date - datetime.now()).days
            if dias <= dias_alerta:
                nivel = "CRITICO" if dias <= 7 else "ALERTA"
                print(f"[{nivel}] {nome} expira em {dias} dias")     ## Monitorar!

Proteja suas aplicacoes contra SQL Injection, XSS, bots e outros ataques na camada 7.

Fluxo de Implementacao IMPORTANTE

6 passos para implementar WAF no F5:

  1. Provisionar modulo ASM: tmsh modify sys provision asm level nominal
  2. Criar Security Policy usando template Rapid Deployment (menor risco de falsos positivos)
  3. Modo Transparent (2-4 semanas): WAF detecta e loga mas NAO bloqueia
  4. Tuning: Revise logs, aceite learning suggestions, crie excecoes para parametros legitimos
  5. Ativar Modo Blocking: Gradualmente, comecando pelas violacoes de alta confianca
  6. Monitoramento Continuo: Integrar logs com SIEM, manter assinaturas atualizadas
NUNCA ative modo Blocking sem pelo menos 2-4 semanas de observacao em modo Transparent. Falsos positivos mal tratados levam a equipe a desligar o WAF.

7. Caso Real: Monitoramento + Automacao para Recuperacao CASO REAL

Como uma empresa de e-commerce reduziu o MTTR de 18 minutos para 2.5 minutos usando automacao F5.

O Cenario IMPORTANTE

Infraestrutura:

  • F5 BIG-IP como load balancer principal
  • Pool com 6 servidores (3 por datacenter)
  • Aplicacao critica de checkout
O Problema (Black Friday): 2 de 3 servidores do DC primario cairam por estouro de memoria. Response time subiu para 8 segundos. NOC levou 12 minutos para agir manualmente. Perda: R$ 600.000+ (R$ 50.000/minuto).

Arquitetura da Solucao

[Zabbix (Monitor)] → [Webhook (Trigger)] → [Script Python (Automacao)]
↓                                           ↓
[Slack (Notificacao)] ←—————————— [F5 BIG-IP (API REST)]

Fluxo de Recuperacao Automatica IMPORTANTE

6 passos automatizados:

  1. Detectar membros down: Zabbix detecta que o pool tem menos de 2 membros disponiveis. Aciona webhook
  2. Tentar reiniciar servicos: Script Python conecta via SSH nos backends problematicos e reinicia o servico (ate 3 tentativas)
  3. Verificar recuperacao: Aguarda 15 segundos e verifica via health check direto se o backend voltou
  4. Ativar servidores standby: Se os primarios nao voltaram, ativa servidores standby do outro DC via API do F5
  5. Redistribuir carga: Aumenta connection limit dos membros saudaveis para absorver o trafego extra
  6. Notificar equipe: Envia relatorio completo para Slack com status final

Conclusao e Recomendacoes

Arquitetura recomendada

[Ansible Tower (Provisionar)] → [Python Scripts (Monitorar + Recuperar)] → [F5 BIG-IP (API REST)]
↓                            ↓
[Git (IaC)]                  [Zabbix/Grafana (Dashboards)]

Para equipes iniciando com automacao F5:

  1. Comece com Ansible — mais facil de aprender e implementar
  2. Evolua para Python — quando precisar de logica complexa e monitoramento
  3. Use os dois juntos — Ansible para provisionamento, Python para monitoramento e recuperacao
  4. WAF em modo Transparent primeiro — nunca ative blocking sem periodo de observacao
  5. Automatize desde o inicio — backups, relatorios e alertas

Proximos passos sugeridos

  1. Configurar lab com F5 VE (Virtual Edition) para pratica
  2. Implementar os scripts de monitoramento em ambiente de homologacao
  3. Integrar com ferramenta de ITSM (ServiceNow) para abertura automatica de chamados
  4. Criar dashboards no Grafana com metricas coletadas via Python
  5. Implementar WAF em modo Transparent e analisar logs por 2-4 semanas
  6. Validar protecao WAF com ferramentas de pentest (OWASP ZAP, Burp Suite)
  7. Implementar testes automatizados para validar as automacoes
